## 二、我的模块理解

<!-- 你负责的模块（M几）要做什么？输入是什么？输出是什么？和谁对接？ -->

**负责模块：**
M3：Agent 编排引擎 
M4：轨迹采集存储

**我的理解：**

M3 主要负责搭建 auto-research 的 agent harness，让 Agent 能根据任务目标生成实验假设、组织实验流程、调用实验执行接口、读取结果并决定下一步动作。输入主要是 benchmark/task spec、baseline 信息、实验预算和当前实验状态；输出是结构化的 experiment spec、Agent 决策记录、best config / best result，以及完整的执行状态。

M4 主要负责把 Agent 运行过程中的每一步记录成可复现、可训练的数据，包括 tool call、实验配置、日志、metric、失败原因、state diff 和最终 reward。输入来自 M3 的状态机和实验执行结果；输出是 trajectory.jsonl、实验 metadata、artifact 路径，以及后续可供数据训练模块消费的轨迹数据。

主要对接对象包括：和吴凡对接 CV 实验平台的 experiment_spec -> experiment_result 接口；和栗维鸿对接 trajectory schema、轨迹质量要求和后续 SFT/DPO 数据格式；也需要和 benchmark / task 负责人对齐任务定义、评价指标和实验预算。

## 四、建议与想法

我初步对自己在 auto-research 项目中关注的重点是：

> 搭建一个可控、可复现、可采集、可扩展的 auto-research agent harness。

这里的重点不是一开始就做出一个“非常聪明”的科研 Agent，而是先把科研实验循环运行起来，并且让每一次 Agent 的观察、决策、工具调用、代码修改、实验结果和反思都能被稳定记录下来。这件事情更可靠，更可行，更可量化，当下更有用。

## 五、本周调研记录

<!-- 自己查了什么资料、跑了什么实验、得到什么结论？附链接或简要记录 -->
本周主要调研了 Karpathy 的 autoresearch 项目。
Karpathy autoresearch 是一个通过强约束实验环境、明确操作手册和 git/tsv 轻量状态管理构成的最小 auto-research harness。它最值得学习的地方，不是某个具体模型调参技巧，而是它如何让 Agent 在一个小而清晰的研究空间里持续产生、评测和保留有效实验。

**思考：**
搭建 auto-research 系统时，只写一份 `program.md` 交给 Codex / Claude Code 是否足够，还是必须实现代码化 harness？

**核心结论: **
不是二选一，而是演化路径：

```text
Markdown protocol
-> coding agent + git/logs
-> Python runner + JSONL trajectory
-> state machine + queue + storage
-> full research platform
```

**Markdown 负责定义研究纪律；代码 harness 负责强制执行系统不变量。**

Karpathy autoresearch 证明：当问题足够小，`program.md` + Codex / Claude Code 可以跑通最小闭环。  
AIDE、MLAgentBench、MLE-bench、MLGym、AI Scientist 说明：一旦要规模化、可复现、可采集、可训练，就必须代码化。
