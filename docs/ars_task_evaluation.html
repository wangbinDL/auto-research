🧪 ARS 任务的评测机制详解

如何用 4 个测试函数"判刑" Agent 写的 R 代码？| Terminal-Bench adaptive-rejection-sampler 深度解析

🎯 一句话回答

不是"判输出准不准"，而是"分 4 关卡"逐步验证：

  1. 📁 文件存在关：你写了文件吗？函数名对吗？
  2. 🔬 能跑关：你写的 R 函数能跑出 1000 个数吗？
  3. 📊 分布形状关：这些数的均值和标准差是不是 ≈ 标准正态？
  4. 📝 输出格式关：你写的 test 函数输出符合 TEST_NAME: PASS 格式吗？

4 关全过 = 通过；任一关失败 = 失败。不是单一指标，是"组合拳"。

📊 评测流程总览

1. Agent 完成任务
→
2. test.sh 启动
→
3. 4 个 pytest 串行执行
→
4. 写入 reward.txt
→
5. Harbor 读取

🛠️ 真实评测入口（test.sh）

#!/bin/bash
# 1. 安装测试需要的 Python 环境
apt-get update
apt-get install -y curl
curl -LsSf https://astral.sh/uv/0.9.5/install.sh | sh
source $HOME/.local/bin/env

# 2. 跑 pytest 跑全部测试
uvx -p 3.13 \
  -w pytest==8.4.1 \
  -w numpy==2.3.3 \
  -w scipy==1.16.2 \
  pytest --ctrf /logs/verifier/ctrf.json /tests/test_outputs.py -rA

# 3. 根据 pytest 退出码写 reward
if [ $? -eq 0 ]; then
  echo 1 > /logs/verifier/reward.txt    # 通过 = 1
else
  echo 0 > /logs/verifier/reward.txt    # 失败 = 0
fi

关键设计：reward 是 二值（0/1），不是分数。4 个测试函数 必须全部通过 才算任务通过。

🔍 4 个测试函数逐个拆解

测试 1️⃣：test_ars_function_exists — 文件存在性检查

目的：确保 Agent 真的"交了作业"

def test_ars_function_exists():
    app_dir = Path("/app")
    ars_file = app_dir / "ars.R"                              # 检查文件
    assert ars_file.exists(), "No ars.R file found..."

    content = ars_file.read_text()
    ars_pattern = r"ars\s*<-|ars\s*=\s*function"             # 正则匹配函数定义
    assert re.search(ars_pattern, content), \
        "No 'ars' function found in ars.R..."

通俗解释

这关干的事非常"机械"，就是检查：

  • ✅ 文件 /app/ars.R 存在吗？
  • ✅ 文件里有 ars <- function(...) 或 ars = function(...) 这样的函数定义吗？

用正则表达式 r"ars\s*<-|ars\s*=\s*function" 容忍空格变化（ars <- 或 ars= 都接受）。

💡 这关的意义 防止 Agent 走捷径：比如 Agent 可能在 README 里写"实现思路"但不写代码。 这关强制代码存在。

测试 2️⃣：test_can_generate_standard_distribution_samples — 功能性测试

目的：确保 Agent 的函数真的能跑、能输出样本

# 关键步骤：写一个 R 测试脚本，扔到 /app 下，调用 Agent 写的 ars()
test_code_r = """
library(stats)
source("ars.R")                            # 加载 Agent 写的代码

normal_density <- function(x) {
    dnorm(x, mean = 0, sd = 1)             # 标准正态密度
}

tryCatch({
    samples <- ars(normal_density, c(-5, 5), n = 1000)  # 采 1000 个样本

    # 三个条件同时满足才算 PASS
    if (length(samples) >= 900                  # 1. 样本数够
        && abs(mean(samples)) < 0.2             # 2. 均值 ≈ 0
        && sd(samples) > 0.8 && sd(samples) < 1.2) {  # 3. 标准差 ≈ 1
        cat("PASS: Generated valid normal samples\\n")
    }
}, error = function(e) {                       # 任何错误都 FAIL
    cat("ERROR:", conditionMessage(e), "\\n")
})
"""

# 跑这个 R 脚本，检查输出含 "PASS"
result = subprocess.run(["Rscript", str(test_file)], ...)
output = result.stdout + result.stderr
assert "PASS" in output, f"Failed to generate... Output: {output}"

通俗解释（"出题"思路）

📚 像老师判作业

老师把学生写的函数 ars() 包装在一个"标准测试"里：

  1. 喂一个标准正态密度 dnorm
  2. 让 ars() 采 1000 个样本
  3. 看采出来的 1000 个数：
  样本数 ≥ 900 个？                    ← 学生至少得跑出 1000 个数
  均值的绝对值 < 0.2？                 ← 真的从"中间"采的
  标准差在 0.8 ~ 1.2 之间？             ← 真的从"标准正态"采的，不是均匀也不是夸张

全满足 → PASS；任一不满足 → FAIL（如 Agent 函数 stop() 抛错，tryCatch 捕获后输出 ERROR）。

关键数字的含义（误差容忍度）

条件阈值为什么？
length(samples) ≥ 900至少 900/1000 = 90%允许 Agent 在采样过程中少量失败（如 log-concavity 检查不过）
|mean| < 0.2均值偏离真值 ≤ 0.2标准正态均值 = 0，1000 样本的标准误 = 1/√1000 ≈ 0.032，0.2 是 6.2σ（极宽松）
0.8 < sd < 1.2标准差偏离 ≤ 20%标准正态 sd = 1，宽松容忍
⚠️ 统计容忍度设计

因为采样是随机过程，如果阈值太严（如 |mean| < 0.05），可能 Agent 写对了代码但被"运气差"判错。0.2 / 0.2 的阈值是统计合理 + 实际可判错的平衡点。

测试 3️⃣：test_has_test_function — 函数存在性检查

目的：检查 Agent 是否写了 test() 函数

def test_has_test_function():
    r_files = list(Path("/app").glob("*.R"))         # 找所有 .R 文件
    test_found = False

    for r_file in r_files:
        content = r_file.read_text()
        test_pattern = r"test\s*<-|test\s*=\s*function"  # 同理正则
        if re.search(test_pattern, content):
            test_found = True
            break

    assert test_found, "No 'test' function found..."

通俗解释

题面要求 Agent 自己写一个 test() 函数做正式测试。这关就是检查：

  • 扫 /app/*.R 所有文件
  • 看有没有 test <- function(...) 这种定义
💡 为什么要求 Agent 写 test 函数？

题面原文："Formal testing is required... with a set of tests where results are compared to some known truth."

评测 Agent 的元能力：不光要会实现，还要会自我验证。这与 Terminal-Bench 失败模式分类中的 "Verification" 维度直接对应。

测试 4️⃣：test_formal_testing_with_known_truth — 行为正确性测试

目的：跑 Agent 写的 test() 函数，检查输出格式

# 写脚本：source Agent 的代码，调用它写的 test()
test_code = """
source("ars.R")
if (exists("test")) {
    test()                                # 直接调用
} else {
    cat("ERROR: test function not found\\n")
}
"""

result = subprocess.run(["Rscript", str(test_file)], ...)
output = result.stdout + result.stderr

# 检查 1：输出必须含 ": PASS" 或 ": FAIL"
assert ": PASS" in output or ": FAIL" in output, \
    "Test function must output results in format 'TEST_NAME: PASS' or 'TEST_NAME: FAIL'"

# 检查 2：必须含 "mean" 统计信息
assert "mean" in output.lower(), \
    "Test output should include mean statistics"

通俗解释（最严格的一关）

📚 像老师让学生自评

老师："你不是说会写测试吗？我现在跑你的测试函数，看它输出对不对。"

  1. 把 Agent 写的 ars.R 加载进来
  2. 调用 test()（让 Agent 自我验证自己的实现）
  3. 检查输出格式：

必须包含的格式（题面要求）：

  TEST_NAME: PASS              ← 通过的测试
  或
  TEST_NAME: FAIL              ← 失败的测试
  Mean: 0.0123 (expected: 0.0) ← 统计量输出
  SD: 0.9987 (expected: 1.0)

这两条断言任意一条不满足 = FAIL。

为什么"检查输出格式"也算"准确"？

题面明确规定：

"Your test function should output results in the format: 'TEST_NAME: PASS' or 'TEST_NAME: FAIL' with mean and standard deviation statistics"

这是题面要求 Agent 必须满足的契约，所以测试函数检查"是否遵守契约"是合理的。

⚠️ 这关的微妙之处

测试 4 不要求 Agent 写的 test() 函数"判定结果对"，只要求它"按格式输出"。

例如：Agent 写 cat("AnyTest: PASS") 也能过这关！

真正判定 ARS 准确性的是测试 2，测试 4 只是检查"自我报告格式"。

🎯 4 个测试的协同关系

📐 评测设计的层次结构

测试检查维度类型失败意味
测试 1 代码是否存在 结构性 Agent 偷懒没写代码
测试 2 采样功能正确 功能性（核心） Agent 算法写错了 / 没真实现
测试 3 test 函数存在 结构性 Agent 没写自检函数
测试 4 自检输出格式 契约性 Agent 不遵守输出约定

为什么需要 4 个而不是 1 个？

🎓 设计哲学：分层验证，捕捉不同作弊模式
  1. 测试 1 防"没交作业"：不写代码就提交
  2. 测试 2 防"写错代码"：这是最关键的功能性检查
  3. 测试 3 防"不写测试"：逃避自验证要求
  4. 测试 4 防"瞎写测试"：测试函数只是装饰品

这对应了 Terminal-Bench 论文中的 "specificity（明确性）" 原则：测试必须捕获所有正确终态。

❌ 典型失败场景

场景 A：Agent 实现了 ars 但写的是常数（rep(0.5, n)）

测试 1 ✅ 通过（文件 + 函数都在）

测试 2 ❌ 失败（sd(samples) ≈ 0，不满足 0.8 < sd < 1.2）

AssertionError: Failed to generate valid normal samples.
Output: ERROR: Mean or std out of range

启示：Agent 想"骗过"测试 1 容易，骗过测试 2 难。

场景 B：Agent 写对了 ars 但没写 test 函数

测试 1 ✅ 通过

测试 2 ✅ 通过（真采样正常）

测试 3 ❌ 失败（找不到 test <- function 定义）

AssertionError: No 'test' function found.
Task requires a function named 'test' that carries out
formal testing of the implementation.

启示：只实现功能还不够，必须满足所有契约。

场景 C：Agent 写了 test 但输出格式不对

测试 1-3 ✅ 通过

测试 4 ❌ 失败（输出 "All tests passed" 而不是 "TEST_NAME: PASS"）

AssertionError: Test function must output results in format
'TEST_NAME: PASS' or 'TEST_NAME: FAIL'

启示：test 函数必须按规定的格式字符串输出，不能自由发挥。

🎓 核心要点总结

评测 ARS 任务的 5 个关键点

  1. 评测的是"组合契约"，不是单一指标
    4 个测试函数分别检查不同维度，全部通过才给 reward=1
  2. 功能性测试（测试 2）是核心
    它真的运行 R 代码并验证统计量（mean ≈ 0，sd ≈ 1），这是最"硬"的检查
  3. 用 tryCatch 捕获错误
    R 函数抛错不算"未通过"，会变成 ERROR 输出，被 Python 端判断为 FAIL
  4. 统计容忍度（0.2 / 20%）是合理设计
    太严会被"运气差"误判，太松会放过真 bug
  5. reward 是二值（0 或 1）
    通过 = 1，失败 = 0。Harbor 只看这个数字，pytest 退出码决定

🔗 与 Terminal-Bench 设计哲学的关联

ARS 任务的测试设计完美体现了 Terminal-Bench 论文中提到的三大质量标准：

  • Specificity（明确性）：4 个测试覆盖了"代码存在 / 功能正确 / test 函数存在 / 格式正确" 4 个明确维度
  • Solvability（可解性）：solution/solve.sh 给出了完整参考实现，证明任务可解
  • Integrity（完整性）：Oracle solution 加密在 protected.tar.gz.enc，Agent 无法看到，避免作弊
